# Android Release Notice Design

The APK-first Android app can notify users when the installed native build is behind an admin-configured release. This is product messaging, not an ad, and never makes the banner image clickable. iOS remains untouched.

`config/mobileRelease` is a server-managed document with `enabled`, `latestVersion`, `latestBuild`, `allowIgnore`, `headline`, `message`, `imageUrl`, and `downloadUrl`. Configuration is off by default. Admin writes require Firebase admin authorization. Public GET returns only a validated, safe subset and never credentials. Enabled configuration requires a positive build integer, semantic display version, and HTTPS APK download URL. `allowIgnore: false` means a current build below `latestBuild` sees a mandatory update; `true` means a dismissible optional update. An installed build equal to or newer than `latestBuild` sees no prompt.

The Android client compares the installed *native* build code, not the downloadable JavaScript manifest version, and checks at launch or foreground resume when its successful fetch is older than 24 hours. A successful response is cached locally; a failed check never newly blocks the app. Optional dismiss is remembered per latest build. Mandatory notices cannot be dismissed by Close, outside tap, or Android Back. Only the Download now button opens the vetted URL. If Android cannot open the configured link, a clearly labeled one-session emergency bypass prevents permanent lockout; the notice reappears on the next app start. The admin can disable the notice to recover from a bad release setting, subject to the app's next refresh.

The notice is presented after the app is ready and overlays the current screen, without interfering with splash/auth resolution. It must display loading/offline and URL-opening errors safely and remain accessible. Tests cover version comparison, optional dismissal, mandatory behavior, failed fetch, rollback, and invalid config. No live mandatory setting is enabled during implementation or test.
